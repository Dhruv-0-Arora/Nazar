# ADR-0010: Authored revert.sh vs Brain-generated fix script are separate artifacts

Status: accepted.

## Context

PLAN M0 says "Write revert.sh: restores the correct env var... Lets you re-run the demo cleanly" and, two lines later, "Server should WRITE the revert.sh script and CREATE the fix".
That conflates two different things with two different trust levels: a hand-authored demo-reset tool, and the Brain's proposed remediation.

## Decision

- `scenario/revert.sh`: hand-authored with the scenario, idempotent, trusted, used by us to reset the demo. Never produced by the Brain.
- `report.json.proposed_fix_script`: generated by the Brain as part of the diagnosis output, displayed in the report, saved in `runs/`. Never executed by the Brain, and not executed on any client during the MVP demo except by a human who has read it.
- If the demo climax includes applying the fix, a human copies the proposed script over, reviews it on screen (that is a feature, not friction), and runs it.

## Rationale

- An offline diagnostic appliance that auto-executes generated shell on sick machines is a different, riskier product; the structured `action_plan` JSON is the deliberate seam for a future autofix API once there is a review/approval flow.
- The demo needs a guaranteed reset path that does not depend on the model having been right.

## Consequences

- Grading gets a second axis: does `proposed_fix_script` substantially match `revert.sh`'s effect? ground_truth.md should state the expected fix so this is checkable.
